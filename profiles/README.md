# CQ Profiles

CQ core should remain generic. Company or team flavor belongs in a profile.

A profile can be tracked in a private fork, kept in a separate private repository, or mounted into a deployment. The goal is to make CQ core easy to upgrade while allowing company identity, routing, and agent prompts to evolve independently.

Artifacts generated by CQ should usually stay out of the profile repo itself. Use ignored local artifacts by default, or a second repo dedicated to worklog/artifacts when a deployment wants durable git history for generated deliverables.

## Suggested profile layout

```text
profiles/<company-or-team>/
  COMPANY.md              # mission, vocabulary, operating boundaries
  agents/                 # deployment-specific agent identities and souls
    ceo/IDENTITY.md
    ceo/SOUL.md
    cto/IDENTITY.md
    cto/SOUL.md
    cmo/IDENTITY.md
    cmo/SOUL.md
  modes/                  # optional mode prompt overrides
  config/                 # non-secret repo/project/routing config
  secrets/                # credentials, tokens, private IDs; ignored by default
```


## Agents vs modes in a profile

A profile should usually define both agents and modes:

- `agents/` contains persistent role identities and souls. Use these when the backend supports durable agents, especially OpenClaw.
- `modes/` contains reusable task lenses. Use these to frame tasks for persistent agents and to give direct `codex`/`claude` runs enough context to behave like the intended role.

For a new deployment, start with persistent `ceo`, `cto`, and `cmo` agents. Let their memories evolve separately, but require completed work to be summarized back into GitHub issues and any profile memory/docs that future agents need.

## What belongs in a profile

- company mission, strategy, taxonomy, and approval boundaries
- deployment-specific agent identities and souls
- private project/repository mappings
- company-specific routing policy
- notification channel names or destinations when safe to track privately
- local operator notes for this deployment, when the profile itself is private

## What does not belong in CQ core

- company secrets
- private board IDs or credentials
- customer data
- proprietary company wiki exports
- official company commitments that are not meant to be public

## Secrets rule

`profiles/**/secrets/` and `*.private.json` are ignored by default. Keep credentials, sensitive local config, local agent/runtime mappings, and machine-specific paths in `profiles/<profile>/config/clawqueue.private.json`, `profiles/<profile>/secrets/`, or environment variables.

For shared profiles, run CQ with `--profile <name>` rather than only `CLAWQUEUE_POLICY_FILE`. That keeps the tracked profile portable while each user loads their own ignored private config from their local checkout.
